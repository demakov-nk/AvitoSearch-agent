# План разработки

Принцип: сначала **тонкий сквозной срез** — программа, которая умеет всё по чуть-чуть и работает от ввода запроса до ответа, — потом наращиваем толщину по этапам. Каждый этап заканчивается тем, что программу можно запустить и показать. Никаких этапов «сделали половину модуля в стол».

## Силуэт проекта (что будет в конце)

```
CLI (запрос пользователя)
   └── цикл агента (agent.py) ── LLM (llm.py, по API-ключу)
              │
              ├── инструменты: свои (tools/) + Авито (MCP-сервер, отдельный процесс)
              │
              └── вокруг цикла: память, права и лимиты, скиллы (md-инструкции)
```

## Этапы

- [x] **0. Скелет проекта**
  Папки и точки входа: `main.py`, `agent.py`, `llm.py`, `tools/`, `skills/`, `data/`, `.env`. Фиксируем стек (агент — Python; MCP-сервер Авито живёт отдельным процессом, его язык нас не касается).
  *Готово, когда:* пустой `main.py` запускается и печатает приветствие.

- [x] **1. Разговор с моделью**
  `llm.py`: клиент API, ключ из `.env`. Пока без инструментов — просто «вопрос → ответ».
  *Готово, когда:* в консоли идёт диалог с моделью; это доказывает, что ключ и доступ работают.

- [ ] **2. Подключение Авито через MCP**
  Запускаем `avito-shopping-mcp` как отдельный процесс, делаем `mcp_client.py`, один раз проходим капчу через `setup` (сохраняем сессию Chrome). Проверяем вручную `avito_search`, `avito_item`, `avito_seller_reviews`.
  *Готово, когда:* все три инструмента возвращают живые данные по реальному запросу.
  *Почему так рано:* это самый рискованный внешний узел (капча, блокировки, поломка сайта) — риски снимаем первыми, а не в конце.

- [ ] **3. Инструменты и реестр**
  `tools/registry.py`: единый список инструментов (свои + из MCP), схемы для модели, вызов по имени. Свои инструменты пока минимальны (например, сохранить черновик ответа).
  *Готово, когда:* из `python3 -c` можно вызвать поиск через реестр.

- [ ] **4. Цикл агента**
  `agent.py`: запрос → модель решает вызвать `avito_search` → выполняем → модель читает карточку → выдаёт ответ. Первый сквозной сценарий целиком.
  *Готово, когда:* на вопрос «найди велосипед до 30 000» агент реально ищет, читает одну карточку и отвечает текстом со ссылкой.

- [ ] **5. Права и лимиты**
  `permissions.py`: лимит шагов, только чтение, запрет одинаковых вызовов, обработка отказов и ошибок (капча, rate-limit) с человекочитаемым сообщением.
  *Готово, когда:* агент корректно останавливается на лимите и объясняет блокировку Авито, а не падает молча.

- [ ] **6. Скиллы анализа**
  `skills/*.md`: инструкции — как разбирать карточку (порядок: цена → описание → характеристики → фото → отзывы), как ставить «да/нет/частично» по критериям, как ранжировать и оформлять итог.
  *Готово, когда:* качество ответа заметно выросло по сравнению с этапом 4 на одних и тех же запросах.

- [ ] **7. Память**
  `memory.py`: только история диалога — сообщения пользователя, ответы модели, результаты вызовов инструментов — в рамках одного прогона.
  *Готово, когда:* на каждом шаге модель видит всю предыдущую историю, и цикл не теряет контекст между шагами.

- [ ] **8. Проверка качества**
  Заготовленные ситуации, как в примере отчёта: скрипт прогоняет запросы с известным ожидаемым результатом (цена в пределах, критерий учтён, ссылки валидны) и считает долю успешных.
  *Готово, когда:* есть цифра «N из M прогонов успешны» — материал для раздела «Проверка» в отчёте.

- [ ] **9. Полировка UX**
  Уточняющие вопросы при неполном запросе, «покажи ещё», «исключи продавца», аккуратный формат выдачи.
  *Готово, когда:* сценарий «запрос → топ-3 с обоснованием → уточнение → новый топ» проходит без перезапуска.

## Порядок — почему такой

Этапы 1–2 снимают главные риски (доступ к модели и к Авито) до того, как на них что-то опирается. Этап 4 даёт сквозной каркас — дальше каждый этап добавляет один слой вокруг него: безопасность (5), качество (6), состояние (7), доказательства (8), удобство (9).
